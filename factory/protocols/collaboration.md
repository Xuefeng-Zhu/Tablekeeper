# Collaboration and delivery

This standing protocol is reusable across products. Product requirements arrive only in the dispatched task. Runtime identities and limits arrive in verified, frozen configuration. Unknown identities or missing spending authorization blocks execution. In balance-only mode, time, token, turn and repair counters do not stop work.

## Work items

Use the empty work-item template. Each item carries its ID, owner and next recipient by literal roster handle, dependencies, state, goal, complete applicable requirements, absolute repository and workspace paths, starting revision, ownership boundaries, acceptance criteria, candidate full commit ID, commands, results, evidence paths, limitations and remaining limits. The coordinator maintains the queue; state changes are material room messages, not substitutes for work.

The executable record uses `id`, `owner`, `dependencies`, `state`, `goal`, `requirements`, `starting_revision`, `workspace_paths`, `ownership_boundaries`, `acceptance_conditions`, `candidate_commit`, `commands`, `results`, `evidence_paths`, `limitations` and `next_recipient`. Requirements and acceptance conditions are lists containing complete text; workspace and evidence paths are absolute-path lists. READY and later work requires nonempty goal, requirements, starting revision, workspace paths, ownership boundaries and acceptance conditions. REVIEW requires candidate, commands, results and evidence. BLOCKED or REJECTED additionally requires `bounded_next_action`; ACCEPTED requires a distinct `reviewer` and supporting `room_event`. Empty templates intentionally fail execution validation until the team completes them.

Transitions:

```text
PROPOSED -> READY -> IN_PROGRESS -> REVIEW -> ACCEPTED
REVIEW -> REJECTED -> IN_PROGRESS
Any state -> BLOCKED
```

READY requires complete inputs, satisfied dependencies, agreed ownership, permissions and verifiable acceptance. Only the owner starts IN_PROGRESS. REVIEW requires a committed candidate and evidence. Independent acceptance binds to that exact candidate. REJECTED records a requirement-linked defect and bounded repair. BLOCKED records evidence, exhausted recovery and a finite next action; it is an outcome, not an indefinite wait. The coordinator may create a replacement READY item after resolving a blocker within existing scope and limits, preserving the original record.

### Shared task board

When `factory_work_item` is available, use it for each material assignment and lifecycle change. Read `factory_task_board` for a compact current index, then `factory_task_board` with `id` for the assigned complete record and version; create with `expected_version: 0` and update with the latest returned version. Supply the complete work-item record with its desired state. Only the coordinator creates PROPOSED/READY items. Nominate an independent roster reviewer before READY; scope, owner and reviewer then remain fixed. Dependencies must already be ACCEPTED before READY or IN_PROGRESS. The board does not send the complete addressed handoff: continue the room protocol below.

The owner publishes IN_PROGRESS and REVIEW. The nominated reviewer sends its verdict to the owner in the room. Begin with `WORK-REVIEW WORK-ID version N ACCEPTED candidate <full SHA>` (or `REJECTED`), using the current REVIEW record version, then include the review findings. Publish ACCEPTED or REJECTED referencing that confirmed message ID in `room_event`. Add separate nonempty `review_commands`, `review_results` and absolute `review_evidence_paths` lists; preserve the delivered candidate, commands, results and evidence. A rejected candidate requires a changed repair commit before another REVIEW. Only the owner changes its own board assignment. Its next admitted turn automatically synchronizes an independent verdict, so `owner_sync_pending` means the board has not yet confirmed the owner's completion. Receipt or turn completion alone never marks work Done.

Use `factory_reconcile_task` with the exact item ID and BAND task UUID after an uncertain write. It only reads; never resend, create a duplicate, or use raw task mutation tools to bypass a pending claim. Keep BLOCKED/ACCEPTED records terminal. Read the live shared board with `band_list_tasks`/`band_get_task`. The separate native agent task list is not a supported surface of this SDK runner.

## Full handoffs and receipts

All assignments, material decisions, defects, deliveries and acceptance go through the bound room using actual verified handles. Do not infer handles from display names or use a local file as the only communication record. Assume a recipient sees only addressed messages.

Every handoff states the focused task, applicable requirement IDs, ownership, absolute paths, starting and candidate revisions, acceptance conditions, evidence and remaining limits. Include complete new or changed requirements inline. Unchanged inherited requirements may use exact absolute read-only source paths and SHA-256 digests when the recipient can read those files; identify the applicable sections. The recipient must read and verify these sources before acknowledging complete inputs or starting work. Unreadable or mismatched sources require a corrected handoff. Message IDs, task IDs, URLs, summaries and instructions to read room history alone do not supply requirements. Do not repeat unrelated future-stage specifications or already verified source text in each assignment.

The runtime assembles numbered fragments before admitting one model turn for the complete payload. Do not create nominal tasks or replies for partial fragments. Use `factory_handoff_ack` with the delivery ID after receiving a complete verified handoff; the tool derives the exact receipt and original sender from authenticated delivery evidence. A confirmed existing receipt is returned without resending. A receipt confirms communication only. If constructing a manual ACK, keep it standalone; local validation rejects malformed protocol text before sending so it can be corrected within the same admitted turn.

For a long handoff, split the full UTF-8 payload into ordered messages. Each part contains one header line, one newline and its exact payload slice. The final fragment adds one newline followed by `END OF HANDOFF`. Concatenate slices without inserting or stripping whitespace; the SHA-256 covers only those concatenated UTF-8 payload bytes, excluding headers and final marker. Each part has the same work-item ID and delivery ID, part index, total count, payload digest and next recipient. The final part says END OF HANDOFF. The recipient acknowledges the complete count and digest only after receiving all parts. It requests missing parts from the sender, takes no action on partial content and ignores duplicate parts with matching identifiers. Conflicting payloads under the same delivery ID are rejected. A retry uses the same delivery identity, so delayed messages cannot start duplicate work.

Use this exact first line for each numbered part, substituting the existing identifiers, digest and verified recipient: `WORK-ID delivery DELIVERY-ID part 1/5; SHA-256 <64 hex characters>; recipient @[[recipient UUID]]`. Identifiers use letters, digits, periods, underscores or hyphens. The final part ends with `END OF HANDOFF` on its own line. Only the header is machine-observed; every part still contains the original payload. Each recipient sends a standalone `HANDOFF-ACK delivery DELIVERY-ID; SHA-256 <same digest>; sender @[[original sender UUID]]` message, mentioning that sender, after receiving every part and checking the full payload digest. Send any review or acceptance separately. This receipt confirms complete communication only; it does not accept the work.

Initial human-authored task dispatches are outside the peer delivery journal. After receiving and verifying every original part, send `TASK-RECEIPT id=DELIVERY-ID; received=4/4; SHA-256 <64 hex characters>` to the actual human sender listed by `band_get_participants`, substituting the original delivery ID, complete part count and payload digest. Keep this exact field format so the receipt remains outside the peer delivery journal. Do not use `HANDOFF-ACK` or `factory_handoff_ack` for this initial human receipt. It confirms communication only and does not accept the product. Peer assignments continue to use the canonical handoff receipts above.

The supervisor persists numbered-send metadata and canonical receipts. After a delayed acknowledgment or failed turn, the frozen watchdog can issue operational notices. In balance-only mode these are advisories, and a notice count does not end work; other policies honor their configured notice cap. It defers notices and notice-exhaustion decisions while the supported SDK still owns queued or processing room callbacks, without extending any operative deadline. Local queue drain is not proof that the remote service has no unseen backlog. Notices identify existing turns or missing delivery parts and do not replace complete task requirements. A non-coordinator sender directs its notice to the coordinator. For a coordinator-originated delivery, the coordinator sends as itself only to that delivery's original unacknowledged recipients: verify and acknowledge the complete original payload, or request missing original parts back from the coordinator. This path is receipt/reassembly only; it never reassigns implementation or invents a new task. No identity is substituted and no synthetic human event is injected. A coordinator failure without an original delivery recipient remains visibly BLOCKED because the SDK filters self messages. Every notice callback is bound to the confirmed event and its exact recipients. A recovery turn or process restart preserves notice history. No notice is sent during another active turn, after any required sender/recipient or cumulative budget is exhausted, or after an uncertain notification result. Unknown delivery and conflicting protocol state block immediately. Unsupported SDK execution state blocks in explicitly configured strict mode; normal balance-only collaboration defers operational notices until callback ownership is known and records the uncertainty without stopping work. Delivery recovery uses existing task ownership, original requirements and remaining limits; a receipt still does not accept the work.

## Membership and delayed peers

Before first delegation, the coordinator verifies all configured seats are in the room. Only the coordinator may add an exact preconfigured missing identity with supported membership tooling. It does not recruit or substitute another seat. On a missing-participant error it attempts the exact add, verifies membership and retries the complete handoff. The coordinator records the observed error and attempted recovery.

In balance-only mode, a delayed acknowledgment prompts diagnosis and coordination rather than a deadline stop. Retry confirmed missing or failed delivery with the same identity and evidence, checking any uncertain outcome before resending. Other policies honor their configured acknowledgment and retry limits. Require acknowledgment and reply evidence rather than relying on process presence or membership alone. If the peer is still unavailable, perform independent unaffected work within limits, then report BLOCKED for dependent work. A missing receipt is not an acceptance.

## Recovery and autonomy

Use the frozen consumption policy. Balance-only mode permits further diagnosed repair while credit remains, without time, token, turn or repair-count stops. After repeated identical failures change the diagnosis or approach; repeating an unchanged command is not progress. Other policies honor their configured limits. The coordinator may replan optional work within scope, but cannot waive required behavior or a failed release gate.

From initial dispatch to the coordinator's final outcome, do not ask or wait for human clarification, approval, confirmation or debugging guidance. Resolve choices from complete requirements and peer evidence. If existing authority or permissions are insufficient, report the concrete blocker as the outcome. No rule here authorizes new spending, publication, submission or broader permissions.

Use expert effort where it affects the work. All seats remain registered; every small edit does not require seven serial approvals. Do not manufacture disagreement, redundant messages or nominal ownership to simulate collaboration.

## Runnable progress

Read `factory_progress` at the start of an admitted turn when available. The frozen policy limits turns and elapsed time before the next runnable checkpoint. Plan only the decisions needed for the next executable slice, delegate it promptly, and perform independent planning for later work without delaying that slice. Preserve complete requirements and independent review.

Use `factory_verify_checkpoint` with the full committed candidate after the configured smoke check is runnable. The factory executes only its frozen command within the remaining turn and session limits, checks the clean candidate before and after, and retains actual results. A failing check or self-reported completion cannot advance progress. A passing checkpoint does not establish independent acceptance or waive any stage requirement. Exhausting the progress allowance is a concrete blocked outcome, not a reason to create another planning item or reset a clock.
