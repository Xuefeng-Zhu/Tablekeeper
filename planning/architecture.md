## 1. Service boundary and incremental delivery

Choose Python 3.12 standard-library HTTP service, `ThreadingHTTPServer`, one process, one state owner, and bundled IANA timezone data via `zoneinfo`. Build from a Python image with timezone data installed during build; verify both mandatory zones inside the resulting image. Bind `0.0.0.0`, honor PORT/default 8080, and return health only after initial state is usable. Ship JSON UTF-8 API errors through one handler. Serve local HTML/CSS/JavaScript assets from the same service in stage 2, including direct navigation to `/`, `/signup`, `/login`, `/lookup`. No hosted services, runtime package downloads, CDN fonts, database daemon or outbound application requests.

Use plain JavaScript modules for the small required browser flow unless Frontend demonstrates a material need for a build framework before implementation. Designer owns the warm hospitality visual system and exact interaction specifications. A framework is not required for state correctness or polish. Python reduces stage-1 dependency/build risk and gives explicit timezone transition resolution. React/Vite plus Node/SQLite is a valid alternative but introduces another dependency/runtime surface without a required durability benefit. SQLite is deferred because state may disappear on restart; introducing it later requires preserving the transaction and export contracts here.

Keep modules separated by responsibility: HTTP parsing/authentication; validation; timezone resolution; domain operations; state/receipts; export migrations; serializers. Stage 3 adds policy/history/series helpers; stage 4 adds the planner. HTTP handlers must not duplicate booking validation. The planner must not call mutating reservation endpoints.

Each stage directory contains a complete service, Dockerfile, RUN.md and local assets. Create stage N+1 only from the independently accepted stage N candidate, then extend that copy. No imports or symlinks to sibling stage directories. Do not backfill later code into an earlier accepted stage. Stage 1 remains API-only; stage 2 receives combined tables/UI; stage 3 receives policies/history/series; stage 4 receives closures/plans/series amendments. Internal forward-compatible data fields may exist earlier; later public endpoints and behavior do not.

## 2. State, transaction and lifecycle contract

The authoritative root contains ordered users/restaurants/tables; password hashes and session-token ownership; reservations with permanent IDs/references; completed receipts; and ID allocation state. Later internal schemas add immutable policies, histories, restaurant revisions, series/membership/scheduled dates, plans and closures. Never derive allocation from list length after import. UUID-based IDs fit 64 characters; generate uppercase alphanumeric references of 6–12 characters and check uniqueness across cancelled and confirmed reservations. Persist successful IDs in records and receipts; failed staging allocations are discarded.

Use one process-wide reentrant lock for every state access, including public availability, authentication session creation, export, reset and import. Parse wire JSON before acquiring the lock; authenticate and resolve receipts against the locked state. For mutations, deep-copy the state into a private candidate, validate and stage all changes there, and replace the authoritative root exactly once on success. On any controlled rejection, discard the candidate; the original root and receipts remain unchanged. Serialization uses detached response values. Serialize immutable snapshots after releasing the lock. Avoid network I/O or async suspension inside the critical section. A failing serialization must be found before commit, not after partial state mutation.

This is the linearization boundary: readers see either the old state or the complete new state. There is no independent occupancy cache to become stale. Derive occupancy from confirmed reservations and, in stage 4, closures. Interval overlap is `a_start < b_end and b_start < a_end` using UTC instants; touching endpoints never overlap. A booking occupies every selected table for its entire interval. Availability and mutation use the same capacity and overlap predicates. One immutable response receipt and all related data changes commit together.

Clone-on-write is deliberately simple. Cost grows with total state size; QA must measure at the supplied fixture sizes with up to 50 concurrent requests and 2 GiB/2 vCPU. If that fails, Backend may replace whole-root cloning with an immutable staged delta under the same lock, after recording evidence; no endpoint contract changes. Do not add multi-worker server processes, which would split memory state. Do not return a 5xx for normal contention. Local mechanism probes are not proof of the 5-second HTTP budget.

Auth uses random opaque non-expiring bearer tokens mapped to user IDs, with multiple sessions allowed. Store salted scrypt hashes (`n=16384,r=8,p=1`, algorithm and parameters alongside salt/hash), never plaintext passwords. Fixture seeding hashes passwords before exposing the replacement state. Do not log credentials or export bodies. Token ownership, hash material and parameters are included in private exports. Keep signup/login/reset hashing resource use bounded; verify concurrent host/container timings before accepting resource limits. Synthetic host scrypt support was observed; image support still needs verification.

## 3. Parsing, errors and idempotency

Reject invalid JSON/non-object mutation bodies with 400 `malformed_request`. A missing required field is 422; a present field with the wrong JSON type normally gives 400, while correct-type bad format/range gives 422. Explicit endpoint overrides win: invalid party size of any type is 422; non-bare local-time strings are 422; moves shape/duplicates, policy invalidity, recurring integer validation and expected revisions follow their explicit 422 rules. Booleans are never accepted as integers. Date parsing must reject impossible calendar dates. Integer query values match ASCII decimal digits only, without signs, exponents or decimal points. Unknown fields/queries are ignored for execution, but unknown body fields still participate in receipt identity. IDs are opaque, at most 64 characters.

For keyed writes, order is: parse JSON object; authenticate; require key (absent/empty => 400); validate key length 1..255 (too long => 422); resolve existing receipt; then endpoint permissions/resources/field validation. Scope receipts by `(user_id, HTTP method, actual route path, key)`. Thus the same key on `/reservations` and `/reservation-moves` is independent, as is the same key at different restaurant policy paths. Do not scope by route template. A successful same-body replay returns status 200 with the original JSON value and bypasses changed resources, cancelled status, newer revisions, cutoffs and permissions that would affect a fresh operation. A differing body returns 409 `idempotency_key_reuse` before endpoint validation.

Store the complete original parsed request and a deep copy of the complete success response. Equality is structural JSON equality: object key order/whitespace do not matter; array order matters; strings/bools/null remain typed; numeric `1` and `1.0` compare equal, but `true` differs from `1`. Unknown values `1.0000000000000001` and `1.0` are distinct and must cause key-reuse rejection. Implement a typed recursive comparison; raw Python dict equality alone is insufficient because booleans equal integers. Do not remove unknown fields or normalize reversed table arrays before receipt comparison. Reject non-JSON NaN/Infinity on parsing. Lossless numeric parsing, comparison, storage and round trip are mandatory, including ignored request fields; no binary float may intervene.

Concrete standard-library strategy: `json.loads(..., parse_int=Decimal, parse_float=Decimal, parse_constant=reject)` for request bodies and stored receipt text. Decimal construction from a JSON numeric token preserves its exact coefficient/exponent. Compare finite Decimals directly, without arithmetic, `normalize()`, `quantize()` or context-limited rounding; compare booleans before numeric types. Validate bounded integer domain fields for finite integral value and specified range before converting them to Python int. Serialize receipt values with a small recursive JSON writer: JSON-escape strings/keys with `json.dumps`, encode lists/objects recursively, write finite Decimal as the unquoted `str(value)` numeric token, handle bool/null explicitly, and reject Python float. This preserves exact values without requiring original spellings or key order. Test tiny exponents, large integers and nested unknown metadata as well as the reported fractional witness.

In the opaque state, each receipt stores `request_json` and `response_json` as JSON **strings containing complete JSON documents**, plus its scope fields. Validate and parse these strings losslessly on import/use. This avoids a caller's ordinary JSON export/import decoder rounding nested receipt numbers: the outer envelope transports them as escaped text. A replay returns the stored response document with status 200; it does not return the enclosing string or a reconstructed live reservation. Domain state stores validated bounded integers and other ordinary JSON values; unknown fields are retained in request_json, not coerced into domain state. Receipt text and private facts commit atomically with the mutation and are exported/imported unchanged. This is a concrete choice within the implementation-defined state format, not a change to the public API. Do not rely on a hash without exact-body equality.

All keyed success paths return 201 initially, including no-op batch/series operations and preview creation; concurrent identical requests yield exactly one 201 and all others 200. Failed operations never reserve a key. Keyed routes are reservations/moves (S1), policies/series adoption (S3), and replan preview/apply/series amend (S4). PATCH/cancel are not keyed.

Private lookup returns 404 for another owner's booking. History, decision and GET series additionally return 404 for missing/invalid authentication; this overrides the general 401. Other protected writes return 401 without valid auth. Managers can publish/plan/apply only at listed restaurants and gain no private diner-read privileges.

PATCH precedence: locate owner-visible record; validate optional expected_revision as a positive non-boolean integer; mismatch => stale_revision before cutoff or proposed field validation; cancelled => reservation_cancelled; check current accepted cutoff; then normalize and validate proposed changes. Cancel checks ownership, then returns the existing state if already cancelled, otherwise checks cutoff. Exact cutoff boundary is refused (`now >= start - cutoff`). Past creation itself is allowed.

For moves, validate the 1..8 distinct-reference shape; resolve ownership and same-restaurant structural requirements; then process per-booking non-occupancy validation in input order, with revision/status/cutoff before proposed values. Complete every non-occupancy check before any overlap check. Stage all resulting records, exclude all listed originals from occupancy, then compare resulting bookings with each other and all unlisted bookings/closures. Include unchanged listed bookings in this final occupancy set. Series amendment uses the same pipeline in occurrence-index order after its required series revision check. Never perform sequential PATCH calls for a collective operation.

Where two unrelated invalid inputs have no prescribed cross-field precedence, use stable required-field/type/resource/grid/capacity validation ordering; QA must avoid asserting an invented precedence. Specified precedence always wins. Map every domain error centrally to the specified code/status and a human-readable message. Unknown resources return the specified 404 rather than accidental KeyError/500.

## 4. Local time and absolute occupancy

Treat local wall times and UTC instants as different types. Parse `YYYY-MM-DDTHH:MM` exactly, without an offset or Z. Resolve the local date's restaurant zone by constructing both fold candidates, converting each to UTC and back, retaining only candidates whose wall value round-trips exactly. No candidate means `invalid_local_time`; two distinct candidates means select the earlier UTC instant. This rejects spring gaps and chooses the first autumn occurrence. Do not rely solely on attaching `tzinfo`, which permits nonexistent wall times.

Generate wall starts from the declared local opens in slot_minutes steps while start < closes. The opening value is a wall-grid origin and need not resolve to a real instant. Resolve **each candidate independently**; omit only nonexistent starts and emit repeated wall times once. Never reject an entire window because opens is in a gap, and never shift its grid to the end of the gap. Berlin 2026-03-29, opens 02:15, closes 04:45, grid/duration 30 minutes, yields exactly 03:15, 03:45 and 04:15, all +02:00. Booking 03:15 must use that same grid and duration predicate. Compute end by adding duration in UTC, then format start/end in the restaurant zone with explicit offsets and seconds. Validate wall start inside the declared interval, wall difference from opens modulo slot_minutes equal zero, and absolute end no later than the effective closing instant. Duration arithmetic never uses same-zone wall datetime addition.

Closing conventions are separate from the definite gap-opening rule. A repeated closing label resolves to its first occurrence, matching the general first-occurrence convention. For Berlin 2026-10-25, 01:30 +90 real minutes ends at 01:00Z, after the first 02:30 close at 00:30Z, and therefore does not fit. A nonexistent closing label is treated as closing at the forward transition instant, the first real wall instant after the gap: the clock has crossed the requested label then. Implement by locating the first round-trippable local time at/after the missing minute (the required zones have minute-aligned transitions); do not shift the grid or delete earlier valid starts. For Berlin 2026-03-29 opens 01:00/closes 02:30 with grid/duration 30, this convention retains 01:00 and 01:30, with the latter ending at the transition 03:00+02:00. Gap-closing is an explicit implementation convention because the specification supplies no instant for a nonexistent close; it is not an independently established normative oracle. QA must keep it distinct from mandatory gap-opening, first-fold booking and absolute-duration checks. Other IANA transitions require the corresponding actual transition instant, not a hardcoded one-hour shift.

Availability includes every valid grid slot even if no seating option fits; a closed day has no slots. Keep fixture order for tables. Sort reservation lists by start instant descending. Serialize created_at once at creation and preserve it forever. Cutoffs compare captured UTC now with the existing start and accepted cutoff. Histories use a nondecreasing timestamp (`max(now,last_entry_at)`) and per-booking seq for total order when clocks/timestamps tie; export preserves strings exactly.

## 5. Portable state and staged evolution

External export envelope always remains `{track:"tablekeeper",format_version:1,state:{...}}`. Give the opaque state its own integer `schema_version` beginning at 1. Use explicit JSON data structures and lists for receipt tuple keys; no pickle, live Python objects, filesystem paths, process addresses or source service calls. An export is a detached atomic snapshot of all state, including hashed passwords, every active token, fixture ordering, all reservation fields, receipt requests/responses, allocation state and future-stage fields. Do not print exports in evidence logs.

Import parses the envelope, validates track/version/state and every internal relationship, then migrates a detached candidate and atomically replaces the root. Wrong envelope/invalid state gives 422 without touching destination state; invalid JSON gives 400. Validate unique identities/references, token owners, table/restaurant references, receipt shape, timestamps, revision/counter types and later policy/series/closure/plan links. Validate according to exported accepted data, not today's policy or today's cutoff. Repeating import restores precisely the exported world, removing destination credentials/receipts as well as reservations. Reset constructs a fresh root, clears all prior state and receipts and establishes initial counters. Export/reset/import get the same serialization boundary as normal requests; target 10 seconds for controls.

Upgrade loaders accept every earlier completed team's schema. S2 migration gives live single reservations `table_ids:[table_id]`, preserving identity/status/times; old receipts remain the original JSON values without added fields. Starting in S1, privately record actual creation, each real amendment (including collective moves), and first cancellation in the same atomic transaction as the record. Each private fact includes ordered seq, captured event timestamp, exact before/after changed fields, resulting internal revision and full immutable policy-0 terms. Preserve original creation values rather than reading the current reservation when building history. No-op, repeated cancel, failure and replay append no fact. S1/S2 public response shapes stay unchanged and no history/decision/policy endpoints are exposed early. Export includes these facts and their provenance; reset clears them.

S3 migration projects these stored facts into public history without inventing events, times or old table choices, retains the accumulated internal reservation revision, and uses the recorded policy-0 terms. Thus an actual S1 create(t1) -> amend(t2) -> cancel has factual created/changed/cancelled entries with their distinct recorded timestamps and resulting revisions 1/2/3; current state is cancelled at t2, original created_at and identity remain unchanged, and the original create receipt still reports its original confirmed t1 response without later-stage fields. Existing S3 histories, accepted terms and all original receipts remain immutable. No migration operation itself is a diner amendment or cancellation.

Fixture provenance differs from observed diner operations. A seed initializes a service record at reset, revision 1 under policy 0; privately mark its initial fact `provenance: fixture_seed` with initial_status and the reset observation time, preserving any timestamp the supported fixture schema actually supplies. Its created field values mean values at service initialization, not a recovered earlier booking. For a fixture already cancelled, do not invent a cancellation event/time or earlier table selection. The S3 history baseline may carry the explicit fixture_seed provenance/initial_status fields alongside its created initialization entry; any later real events carry their recorded facts. This convention distinguishes initialization from a diner operation and keeps seed revision 1. Import preserves that baseline rather than reseeding. All team's valid S1/S2 exports must already carry this ledger/provenance contract; no product has yet shipped a schema lacking it. Missing required ledger data is invalid state for these schemas, not permission to fabricate historical facts. If a future accepted source schema genuinely lacks facts, define an explicit truthful migration before accepting that schema.

Maintain original receipt values even if they lack newer response fields. Future live GETs expose current-stage fields, but a replay is the old original response. Restaurant revision is tracked internally from S1 (reset 0, fixture seeds do not count) so upgrades preserve subsequent write counts. S3 series metadata includes original scheduled local dates, current references, exception flags and revision. S4 migration initializes closures/plans empty for older states. S4 exports include stored preview plans and applied flags so references/retries and stale-plan checks remain meaningful after import. A stage accepts its own exports and all earlier completed stage exports; accepting future schemas is not required.

## 6. Combined tables, policies, history and agreements

Represent selection internally as a list of one or two IDs. Validate membership within restaurant, duplicate IDs, mutually exclusive table_id/table_ids and pair declaration. More than two or undeclared pairs => combination_not_allowed; duplicates/both fields => validation_failed. Normalize an accepted pair to its declaration order; reversed input is the same domain selection. Single response includes both table_id and table_ids from S2 onward; pair response omits table_id. Availability lists eligible singles first in fixture order, then eligible pairs in declaration order. Pair capacity is summed; all members must be free. No transitive combinations. Ordinary PATCH and batch moves share this normalization.

Policy selector chooses max `(effective_from,policy_version)` among dates <= resulting local start date, else policy 0. Version allocation follows publication order, independent of date order. Policies are immutable complete records with exact table capacities, bounded non-boolean integers, valid date and no duplicate weekdays. Fixture detail always stays original. Policy publication has no retroactive effect. Explanations compute capacity and no_overlap independently for every single table, in fixture order and fixed rule order, reporting selected policy_version; without explain=true omit explanation fields while retaining inherited stage-2 available_options.

Reservation accepted_terms is a complete deep copy excluding effective_from. Store absolute end at acceptance. Real amendment checks old cutoff, validates all resulting fields against selected new policy, and atomically adopts terms/end, increments reservation revision once and adds one changed history. No-op still requires confirmed/editable state and expected revision checks, but preserves terms/end/revision/history even if current policies differ. A real cancel increments revision and adds one terminal cancelled history; a repeated cancel changes nothing. History changes have fixed field order; single-to-single uses table_id, operations involving a pair use complete before/after table_ids. Created records include all three logical fields. Reassigned always uses table_ids and plan_id. Every history entry freezes resulting revision and terms.

Series adoption stages all count 2..12 occurrences; interval_weeks 1..4; validates anchor ownership/status/cutoff/nonmembership, then each generated occurrence by ascending index. Calendar-add weeks to the anchor's local date, never add seconds to UTC. Each generated booking independently selects its policy and resolves DST. Anchor is occurrence zero with all reservation fields/history/receipts untouched. Membership belongs in series state, not a rewrite of anchor response. Atomic failure includes ID/version counters. Preserve each scheduled local date separately from subsequently edited current starts.

Individual real PATCH or collective diner move sets permanent exception=true; cancel does not. Each affected series increments once per operation, not once per member. A cancelled anchor leaves siblings intact. Series amend selects noncancelled, nonexception indices >= from_index, uses original scheduled dates plus requested time and current tables/party, applies amendment rules atomically and never creates exceptions. Empty/all-no-op eligible sets succeed without revisions. Replan movement preserves exception flags and scheduled dates and increments each affected series once.

Restaurant revision increments once per successful new booking, real PATCH, first cancellation, policy publication, whole series adoption, real moves batch, real series amendment or plan application. No increment for seed/reset baseline, failures, no-ops, preview or replay. Reservation/series/restaurant revision changes are accumulated as sets in the transaction to prevent double increments. A plan application increments restaurant revision even with zero moved bookings because it installs a closure.

## 7. Deterministic replan algorithm and atomic application

Authorize manager, validate explicit-offset from/to instants and strict from<to, restaurant and table, then planning limits (up to 6 restaurant tables, 4 declared pairs, 6 confirmed bookings intersecting closure). Consider every confirmed booking at that restaurant whose absolute interval overlaps the proposal; all others are fixed. Option ranks are global fixture-single then declared-pair order. For each considered booking, evaluate capacity under its own accepted_terms, preserve its absolute interval and remove options colliding with fixed bookings, existing closures or proposed closure. Cancellation cutoffs do not constrain repair.

Sort considered bookings lexically by reference. Exhaustive depth-first assignment visits ranked candidates; reject conflicts with previously assigned bookings immediately. At a complete feasible assignment compare tuple `(changed_count,total_unused_seats,rank_vector)`. Changed means normalized set differs, regardless of input ordering. Use branch-and-bound only with admissible lower bounds; traversal order alone does not implement the second objective. At most ten options per six bookings gives 1,000,000 unpruned leaves. Precompute pairwise option conflict masks and per-option capacities/costs; immutable prepared arrays keep the inner loop small. No heuristics or cutoff may return a nonoptimal plan. No feasible assignment => 409 no_feasible_plan with no stored preview/receipt/counter change. Empty considered set has a feasible empty assignment and zero objectives.

Preview stores plan ID, exact restaurant revision, normalized closure and complete assignments/score; no occupancy or reservation change. At apply, replay resolution happens first, then resource/manager checks, then already-applied rejection before stale revision for a new key. Require recorded restaurant revision equal current revision. The serial transaction installs closure, changes all moved table sets with reassigned history/revisions, updates affected series once, marks the plan applied, increments restaurant once, stores response and receipt. Return all considered bookings in reference order, including unchanged ones. Other restaurants' writes do not invalidate it. Applying under another key after application returns plan_already_applied; a successful key always replays. Stored revision protects against intervening booking, policy, series and closure changes.

## 8. Browser/server contract for Designer and Frontend

Use one monotonically increasing search generation covering restaurant metadata, availability, labels and booking selection. Capture restaurant/date/party inputs with each request. Apply results only if that generation is current; AbortController is an optimization, generation checking is the correctness mechanism. A newer accepted search invalidates the old selection; an older response cannot reopen it. Handle metadata and slots as one matched result so stale labels cannot describe new IDs. Availability cells reflect server IDs exactly, never optimistic occupancy.

Model selected booking form separately from search controls. A form holds semantic selection plus an immutable pending `(key,body)` attempt and state idle/submitting/confirmed/rejected/uncertain. Re-submit unchanged fields reuses the same attempt even after success; actual user changes make a new attempt. Capture submitted body/key before awaiting fetch and ignore stale completions from superseded attempts. Unknown outcomes retain the immutable attempt and show nonempty booking-uncertain without booking-error or a new confirmation. Only a parsed successful server response supplies confirmation. An explicit rejected response shows booking-error; table_unavailable refreshes availability but preserves selection and inputs for correction. Refresh is generation-guarded and cannot erase the retained form. Successful retry clears error/uncertainty and displays the server's original reference exactly.

Separate draft edits from the retained uncertain request so changing and reverting fields cannot accidentally mutate an in-flight body. Same-form unchanged retries keep body JSON values identical, including legacy table_id after upgrade. No page reload/cross-tab recovery is required. Keep bearer token and display name stable through same-origin navigation; signout clears local auth; current-user appears everywhere signed in. Import preserves bearer validity and receipt identities; the open browser must not rebuild pending keys because a server upgraded. No new policy/history/replan screens or batch UI are required. Later lookup/confirmation must use current API values where requested, and old replay receipt shape must remain displayable.

Required test IDs and human labels come from the original specification, not new architecture names. Designer must document desktop and 375px layouts, visible labels/focus/contrast, unavailable/selected/loading/empty/refused/uncertain/success states and combined-table labels before UI implementation. Frontend and QA should agree on delayed response, post-commit response loss, conflict-refresh and upgrade tests from those states. Architecture is ready for their challenge, not a claim that cross-owner agreement has already occurred.
