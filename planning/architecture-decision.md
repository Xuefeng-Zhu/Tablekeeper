## Options and evidence

Select Python 3.12 standard-library HTTP API, SQLite and ZoneInfo; Stage 2 adds React with TypeScript and Vite compiled assets. The proposed TypeScript API would share a language with the browser but would require an additional timezone implementation and SQLite binding. Python supplies both backend mechanisms through standard library APIs and keeps the API image small. A hosted database or auth service violates offline runtime. A mutable global dictionary could work but puts rollback and snapshot discipline entirely on custom code; SQLite supplies explicit commit/rollback while retaining a simple single-process model. Multiple workers are unnecessary and would complicate occupancy serialization.

Use ThreadingHTTPServer with an explicit request backlog at least 64 and daemon request threads, one SQLite connection opened with check_same_thread=False and isolation_level=None, protected by one process-wide threading.RLock. No unguarded database access; no second process or worker. JSON transport, routing and typed validation remain separate modules. This is a task-sized choice; HTTP request handling must be verified against real clients and malformed requests, not inferred from library availability.

ZoneInfo depends on included IANA data; fold selection and SQLite threading controls are documented in the official [ZoneInfo](https://docs.python.org/3.12/library/zoneinfo.html) and [sqlite3](https://docs.python.org/3.12/library/sqlite3.html) documentation. These establish available mechanisms, not our product correctness. [hashlib](https://docs.python.org/3.12/library/hashlib.html) documents scrypt; OpenSSL-backed availability must be checked in the chosen image.

### State and transaction boundaries (S1 §§1,7,10,11; S2 concurrency)

The exact portable schema is in architecture-state-schema.md. SQLite is in-memory: disk durability is out of scope. Store entities in explicit keyed tables with JSON payloads where preserving ordered fixture/response data matters. Use parameterized SQL. Every request's database-dependent phase, including authentication lookup and reads, runs under the same lock. Writes use explicit BEGIN IMMEDIATE, validate against the transaction's state, commit once, and rollback on any error. Reads materialize a response inside the lock, then send detached bytes outside it. Never stream live state. Parsing bytes before acquiring the lock is safe; endpoint decisions, receipt lookup and all state checks are inside it. No network operation occurs under the lock.

Each write returns a detached JSON value after successful commit. A disconnected socket after commit cannot undo state; receipt is already durable within the running process. Socket failures are transport events, never a reason to rerun the command. Expected bad input produces the prescribed 4xx envelope, not uncaught exceptions. Defensive error handling does not excuse a 5xx: all observed 5xx are release failures. The lock makes complete reads and writes admit a serial ordering, including reset/import/export; validate this with independent HTTP races. Atomicity covers entities, occupancy, receipts, histories and all applicable counters.

Occupancy uses integer UTC microseconds and a.start < b.end AND b.start < a.end, plus nonempty intersection of table sets in the same restaurant. Cancelled rows never occupy. For a collective operation remove every listed member's old assignment from the hypothetical occupancy set, then insert ALL resulting members, including unchanged members, and compare them together with all unlisted fixed occupants. Swaps can succeed; transient sequential PATCH calls are forbidden. Stage 4 closures use the identical half-open predicate. Availability is an ordered projection of the same seating/time predicate used by writes, not a separate approximation.

### HTTP parsing, routing and error precedence (S1 §§3,5–8,11)

API responses use application/json; charset=utf-8. A 204 has no body. Parse strict JSON (reject NaN/Infinity), require an object for body endpoints, ignore unknown fields for validation while keeping them in the receipt body. The general rule is wrong recognized field type ->400 malformed_request; missing required field and correct-type invalid format/range ->422 validation_failed, subject to every endpoint-specific override. Import is an explicit S1 §10 override: malformed JSON ->400 malformed_request; any parseable invalid envelope or state (including wrong recognized field JSON types) ->422 validation_failed with no destination change. Do not coerce strings/booleans into integers. party_size's explicitly invalid values, including strings/booleans, are 422; a nonstring starts_at_local is 400 while any malformed local string is 422. Batch shape and references use the explicit 422 overrides. Policies, expected_revision and series integer inputs use their explicit 422 rules. Query integers match ASCII decimal digits only, including leading zeroes; signs, exponent, decimal point fail 422. IDs at most 64 characters; idempotency keys 1..255, absent/empty 400. Unknown query fields ignored.

Routing must match method and full path before dispatch, decode path segments consistently, and use that routed path as receipt scope without query parameters. Public: health, reset/import/export, auth signup/login, restaurant list/detail, availability and later policy list. Ordinary reservations require bearer auth; inaccessible reference is 404. Stage 3 history/decision/series GET return 404 even without authentication; do not pass them through the general 401 middleware. Series adoption/amend requires auth; manager policy/replan routes require auth then restaurant existence then manager permission, except completed receipt resolution precedes current-resource checks.

For idempotent writes: strict object parse, authenticate, validate required key's presence/range, resolve completed receipt, THEN endpoint fields/resource permissions/current state. Record-only successful 201; no claims for failed 4xx. Canonical equality recursively sorts object keys, preserves array order and scalar types, treats parsed numeric equal values as equal (1 and 1.0), distinguishes booleans from numbers, normalizes negative zero, and preserves ignored fields. Do not use Python == alone, because True equals 1. Receipt stores the original parsed body and detached response, keyed by (user_id, method, path, key). Never regenerate an old response through the current serializer. Concurrent same-key calls yield one 201 and remaining 200; conflicting JSON yields 409 even if invalid under current rules. Different path/user remains independent. Replays do not touch state or counters.

Explicit ordering: repeated cancel returns current cancelled record before cutoff. PATCH rejects cancelled and applies current-start cutoff; S3 valid stale expected_revision precedes cutoff/change validation, malformed expected_revision is 422. In a batch validate structural shape/distinct references, then items in input order; each item's accessibility/same-restaurant/cancelled state, valid stale revision and existing cutoff precede that item's change validation. Only after all non-occupancy checks compare resulting occupancy. These phases implement explicit overrides; broader combinations of unrelated errors not ordered by source remain conventions, not new acceptance rules. Chosen ordinary change-validation order is recognized field shape/range, restaurant/table membership, local existence, opening window, grid, capacity, occupancy. Source-specific overrides always win. Record unexpected multi-error disputes for PM; no silent requirement waiver.

Authentication: exact stored email identity (no invented case-folding); minimal local@domain format, signup password >=8, duplicate 409 email_taken, login unknown/wrong 401. Store random 16-byte salt plus scrypt n=16384,r=8,p=1,dklen=32 and algorithm parameters, never password. Compare digests with hmac.compare_digest. Generate opaque tokens with secrets.token_urlsafe(32); store token -> user, never revoke earlier token on login, no expiry. Seed passwords use the identical hash function immediately. No hardcoded credentials. New IDs use random opaque strings <=64; reference uses collision-checked 10-character uppercase alphanumeric, immutable globally across confirmed/cancelled bookings. Timestamps created once. Unknown references and owner mismatch share 404.

### Time contracts (S1 §§4,8,9; Q07,Q09,Q10)

Local date YYYY-MM-DD and local start YYYY-MM-DDTHH:MM are strings validated by regex then real calendar parsing. Persist starts_at_local unchanged after validation plus UTC start/end integers and explicit-offset response strings. Creation/history timestamps use UTC +00:00, never Z. List sorts by instant descending; tie order is an implementation convention. Past booking is permitted. Cutoff rejects now >= current_start - accepted_cutoff; equality is blocked. Capture now once per operation after lock admission. A clock interface allows exact cutoff tests through unit dependency injection, not an undocumented delivered test endpoint.

Resolve local start by trying folds 0 and 1, converting each to UTC and back, retaining only exact local round trips and choosing earliest distinct UTC instant. No candidates means invalid_local_time. This rejects gaps and chooses first repeated occurrence without hardcoded transition dates. Compute end as UTC start plus duration, then render in zone; never add duration in zoned wall time. Enumerate local opens + k*slot_minutes, skip nonexistent candidates, deduplicate local labels, compare absolute end <= resolved closing instant. Closed weekday gives slots []; valid slots with no fitting seating remain with empty IDs. Grid is anchored to opens, never midnight.

Unspecified endpoint convention: repeated opening/closing endpoints resolve first; a nonexistent endpoint advances to the first valid local minute on that date for boundary comparison, while the local slot grid remains anchored to the configured opens. This convention does not alter required unique-endpoint examples. Berlin 2026-03-29 01:00..03:30 grid30/duration90 yields only 01:00. NY 2026-11-01 00:30..02:30 yields 00:30,01:00,01:30. Berlin fold 02:30+02 ends03:00+01, NY fold01:30-04 ends02:00-05, spring Berlin01:30+01 ends04:00+02. Q10 independently verifies all examples in the delivered image.
