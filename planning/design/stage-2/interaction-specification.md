## Visual concept and reusable components

A contemporary restaurant menu: warm ivory paper, deep forest ink, serif editorial headings, thin rules and generous space. The distinctive element is the time-led seating list: a large local time sits beside plainly named seats, with approved pairs styled as intentional options headed “Together at two tables.” Restaurant names and table labels are the information hierarchy, never raw IDs. No invented restaurant imagery, reviews, locations or popularity claims. The brand wordmark is text “Tablekeeper”; a small decorative line motif is optional. No illustration dependency.

Use [tokens.css](tokens.css) as the concrete palette and sizing reference. Heading stack `Georgia, 'Times New Roman', serif`; body stack `'Trebuchet MS', 'Segoe UI', sans-serif`; these are system fallbacks requiring no runtime fetch. Font variation across systems is expected and must not break layout. Headings regular weight; body 400, control/section emphasis 600 or 700. Desktop hero 48px/1.08, mobile 36px/1.12; page title 32px/1.15 (28px mobile); section 24px/1.25; body/control 16px/1.5; secondary 14px/1.5. Never shrink inputs below 16px. Times and references use tabular numerals; references permit text selection.

Components: shell/header/navigation, page introduction, labelled field with hint/error, primary/secondary/text/destructive action, feedback panel, submitted-query heading, time section, seating option, booking card, reference receipt and reservation detail. All use the same spacing scale and control treatment. Surfaces have 1px warm-neutral borders and 12px radii; main search/booking panels 16px. Avoid giving every text block a card. Use shadow only for the booking panel and focused floating-free surfaces. Controls are at least 44px high; option buttons at least 76px high with 12px padding. Primary filled forest with white text; secondary white with strong border and ink; destructive red text/border on white, never the most prominent action on search.

Colour never carries a state alone. Available: white surface, strong border, “Available · up to N guests.” Unavailable: muted surface, readable secondary text, “Unavailable for this search”, native disabled button. Selected: forest-tinted surface, 2px forest border, visible check and “Selected.” Pair: small “Two tables together” eyebrow plus both labels; no extra invented seating category. Loading: plain progress copy and optional CSS spinner with hidden decorative semantics; no pulsing skeleton required. Success: green panel/check and heading. Refusal: red panel/exclamation and corrective sentence. Uncertainty: amber panel/question and explicit unknown-outcome copy. Focus is a 3px blue outer ring with 3px offset; selected border remains distinguishable inside it. Disable opacity tricks that reduce contrast.

## Navigation and journeys

All four URLs return HTML and work directly. Header links: Tablekeeper → `/`, “Find a table” → `/`, “Your reservation” → `/lookup`. Signed out: “Log in” → `/login`, “Sign up” → `/signup`. Signed in: `current-user` contains the display name and `logout-button` says “Log out” on **every** screen. Active destination uses underline and `aria-current="page"`. Header is not sticky, avoiding occluded focus at narrow widths. Main begins with a skip-link destination and one h1. Do not add required routes or invented mandatory testids.

1. Browse: arrive `/` → choose restaurant/date/party → “Find a table” → review submitted restaurant/date/party/timezone → choose an available seat. Browsing works without authentication. Initial instruction: “Choose a restaurant, a date and your party size to find your table.” No automatic initial availability request is necessary.
2. Signed-out selection: remain on `/`; show `auth-error`: “Log in or sign up to book this table.” Include ordinary login/signup links; focus the error panel programmatically. Do not submit or invent a hold. Preserve the search bundle at app level across client navigation; after successful authentication return to `/` and tell the diner “You’re signed in. Choose a table to continue.” Do not auto-book or imply an old option is guaranteed.
3. Signed-in selection: snapshot the accepted option, open the booking card and focus its heading. Read summary, optionally change booking party size, submit. A selected option is not reserved yet; helper says “Your table is reserved only when a confirmation appears.” Server decides capacity and availability.
4. Confirmation: same page and still-visible selected form; reference receipt appears immediately below its submit/feedback area. “Your table is booked” and “Keep this reference for your reservation.” Lookup link navigates to `/lookup` and may prefill the reference through app state. Repeat submission of the unchanged form is available and must reach the server.
5. Manage: `/lookup` → sign in if needed → enter reference → “Find reservation” → restaurant, every selected table, date/time/zone, party and exact status → cancel. Cancellation success changes status in place and removes the cancel action. No amendment/batch/policy/recurring UI is required in Stage 2.
6. Logout clears local session and invalidates user-specific form/lookup callbacks. Keep public search browsing available. Move focus to the main page heading and announce “You’re logged out.” Do not erase session on mere network failure; state import is not logout.

## Screen hierarchy and responsive layout

**Search `/`:** compact header; small “MAKE TIME FOR A GOOD MEAL” eyebrow (decorative optional); h1 “A place at the table.”; one-line explanation; search panel; submitted-query results heading; availability and booking area. Desktop max content 1200px, outer gutters 32px at >=1024px, vertical page spacing 40px. Search form is a wrapping grid: restaurant widest, date, party, action. At >=1024px, results/form columns `minmax(0, 1fr) 340px`, gap 28px; no booking selection means results use full width. Booking card is in ordinary document flow, not sticky. Before selection, the sidebar can be absent rather than display filler.

**Availability:** one `availability-grid` container holds time sections in returned order. Each section has an h3 local HH:MM and wrapping option-card grid (`repeat(auto-fit,minmax(min(100%,180px),1fr))`). All single tables appear in fixture order, including unavailable cells; then available pair cells in declaration order. Each pair's labels follow its declared member order. A section is a visual row, not a fixed-width HTML table. Use semantic sections/lists and native buttons, not ARIA grid, so ordinary Tab navigation works without fabricated arrow-key behavior. Capacity is factual “Up to N guests.” Repeated labels remain legal; use time/capacity in accessible names but do not rename fixture labels. Every slot includes all singleton cells even if no available option exists. No virtualisation, hiding or collapsing required cells. Do not replace a nonempty slot list with an empty-state container.

**375px:** outer gutters 16px, available width 343px; header wraps onto a second line with 12px gaps, display name wraps anywhere. h1 36px, section gaps 24px. Search fields stack in restaurant/date/party/action order, full-width controls. At <1024px availability and booking stack, with booking after the grid in DOM and visual order. Selecting a seat focuses and scrolls to the booking heading, so the form is discoverable even after a long grid; add “Back to seating options” anchor to the results heading. At <600px each time section's cards form one column. Dates, table labels, restaurant names and references wrap; never truncate the only copy of a label. Set all grid/flex children `min-width:0`; inputs width 100%, `box-sizing:border-box`; text overflow-wrap:anywhere where fixtures may be long. No fixed width or unbroken inline pair string may expand the page. Do not use global overflow-x:hidden to conceal layout failures. Arbitrary fixture table count grows vertically, not horizontally. At 600–1023px cards may wrap into multiple columns and forms remain stacked below results.

**Authentication:** same shell, max-width 440px panel, left-aligned title and copy; fields stack; submit full width; alternative-auth link below. Signup title “Join the table”; visible labels “Display name”, “Email”, “Password”; hint “At least 8 characters.” Login title “Welcome back”; Email/Password. Password remains masked. `autocomplete` name/email/new-password/current-password as appropriate. Preserve email/name after refusal; do not log password or retain it after successful auth. Submit labels “Create account” / “Log in”, pending “Creating account…” / “Logging in…”. Authentication success replaces provider state and returns to search, or returns to `/lookup` when login began there. Client route transitions focus destination h1.

**Lookup:** main max-width 760px, h1 “Your reservation”, supporting “Enter the reference from your confirmation.” Reference field + submit wrap/stack at mobile. Signed out: “Log in to look up your reservation” with login/signup links; public lookup page remains reachable. After login retain the draft reference, but require explicit lookup. Found record shows restaurant as heading, a definition list for local start/timezone, party, all table labels, reference and status. Status badge text itself is exactly lowercase `confirmed` or `cancelled`; any introductory “Status” belongs outside it. Reference is text, not an ID dump. Cancellation uses “Cancel reservation” destructive secondary button with nearby “Cancelling releases all tables in this reservation.” No modal confirmation is required; the explicit labelled action is the cancellation. Pending disables that button, “Cancelling…”. Success focuses status (tabindex=-1) and announces cancellation; removal of the button must not lose focus to body.

## Controller contract: presentation must preserve ownership

- Search list request has its own loading state. Every explicit availability search increments searchGeneration and captures immutable restaurant/date/party. Detail and availability must both succeed before publishing one accepted bundle. Grid, heading, label lookup, dates/zone, option handlers and form creation use it exclusively. Draft controls never relabel old results. Guard success, failure and finally; abort alone is insufficient. New search clears selection/feedback and invalidates old form callbacks immediately. B remains B after any delayed A response.
- Each selection snapshots restaurant name/id/timezone, labels/IDs, exact returned starts_at_local and searched party. Never derive request wall time from browser timezone. Refreshing availability cannot replace or unmount this snapshot; on conflict it stays even when its cell disappears. When unavailable after refresh, the selected cell may become disabled, but the form heading still names the original selection and explains refusal. Selection is not inferred from grid membership.
- Form semantic change (party or choosing a different option) increments form revision, clears prior confirmation/error/uncertainty, and invalidates prior attempt. Changing away and back is still new. Selecting the identical option without a semantic change does not discard a pending identity. An old network operation may still have committed; ignore obsolete callback and never transfer its outcome to the new form. Brief helper after editing an uncertain attempt: “This change starts a new request; the earlier outcome remains unknown.” This is advisory text, not booking-uncertain for the new attempt.
- First submit freezes body, serialized bytes, owner, form revision and random key before I/O. Single payload uses table_id; pair payload uses table_ids in declaration order. Unchanged retry/repeat-success submit uses **the identical body and key** and reaches the server. On pending repeat send clear prior feedback/confirmation; subsequent lost replay response becomes uncertain. Never use cached success as the response.
- Request timeout is 8 seconds. Transport error, timeout, malformed/truncated/non-JSON success is uncertain, not rejection. A valid 201/200 reservation response confirms and clears both feedback elements. A structured confirmed rejection shows booking-error only. Preserve input/body/key on refusal and uncertainty. Do not render absent error elements as empty hidden nodes: conditional mount only.
- 409 table_unavailable triggers one guarded refresh for the submitted search, with refresh generation plus captured searchGeneration/formRevision/attemptId. Refresh affects availability only, not error/form. Do not auto-pick a replacement or retry. Later new search/refresh supersedes old work. Error and uncertainty are mutually exclusive for the current attempt.
- Session provider and pending attempt survive route state as specified by architecture, no reload during import. sessionStorage with guarded access backs token/profile, with memory fallback. No tokens in URLs/logs. All routes eagerly bundled; no service worker, polling or cross-tab synchronization. Between-request import does not clear current-user, selected form or retry identity. Legacy replay table_id is adapted to a display array at the view boundary only; original server receipt JSON stays unchanged.
- Confirmation reflects the actual response, including every member, local start and restaurant label. When showing an original receipt after later mutations, label it “Booking confirmation”; do not claim it represents newly fetched current status. Lookup is the current-status path. Never turn a replay into an additional booking.
- Lookup increments a separate generation for each submit; clear prior detail/error on new lookup, fetch protected reservation and corresponding restaurant labels under that generation, publish together. Cancel captures generation/reference/session and cannot overwrite a later lookup. If cancellation response has unknown outcome retain last-known status with explicit warning and offer lookup. Encode opaque path segments. No browser PATCH/batch or manager controls.

## Accessibility and acceptance conditions

Native associated visible labels are mandatory; placeholder is supplemental. Group related search and booking fields under headings; link hints/errors via aria-describedby. Buttons have explicit type. Show each available option's labels/time/capacity and selected text; unavailable options remain readable though omitted from Tab order. Every enabled action works with keyboard. Focus order follows shell → search fields → enabled options in returned order → booking → lookup link. On deliberate option selection focus heading (tabindex=-1); route changes focus h1; errors and confirmations focus their feedback heading; background refresh never steals focus. No positive tabindex, trap, hover-only content or color-only legend. Use polite role=status for loading/success/uncertainty and role=alert for actual errors; do not announce the entire grid as a live region. Avoid duplicating a spoken message in multiple live nodes.

Normal text contrast >=4.5:1, large text >=3:1; control outlines/focus/meaningful icons >=3:1 against adjacent surface. Token contrast is computed by the accompanying check, but browser QA must verify actual computed styles including hover/disabled/selected. Essential unavailable text remains >=4.5:1. Links use underline in prose. 44x44px minimum action targets; menu links get adequate padding. Reduced-motion disables spinner animation/scroll animation; no required animation delays. Browser text enlargement to 200% must retain usable controls and wrapping. At 375x812 and 1440x900, document scrollWidth must not exceed clientWidth; inspect a long-label/many-table fixture as well as ordinary data. Never hide failing horizontal layout with clipping.

Build acceptance requires the exact selectors, coherent hierarchy, every named state, preservation of server/retry/generation contracts, keyboard operation, measured contrast and both viewport reviews.
