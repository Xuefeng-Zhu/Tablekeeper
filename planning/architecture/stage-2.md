## A. One canonical seating selection

S2 Model/API/Combined tables: add `combinable: string[][]`, default `[]`, to normalized restaurant configuration and schema 2. Preserve table fixture order, pair declaration order and member order of each declared pair. A declaration consists of exactly two distinct existing table IDs of that restaurant. Reject invalid declaration types/shapes/references atomically with shared validation codes; duplicate unordered declarations are treated as invalid fixture configuration (422), a deterministic choice for an unspecified invalid-fixture case. Do not infer transitive combinations or arbitrary sums of capacities.

Implement a shared pure `normalizeSelection(restaurant, input, prior?)` used by create, PATCH, each batch move and fixture/import validation. Use own-property presence, not truthiness, to detect supplied selection fields. Supplying both table_id and table_ids gives 422 validation_failed even if one is null. If neither is supplied, PATCH/move retains the complete old set; create requires one. A lone table_id normalizes to one member. table_ids must be an array; empty gives 422 validation_failed, duplicate member gives 422 validation_failed, more than two distinct members gives 422 combination_not_allowed. Array and member wrong types use S1's 400 malformed_request; string ID range/format errors use 422. Missing table/foreign-restaurant member gives 404 not_found. For two valid existing IDs, find their unordered set in declared combinations; absent is 422 combination_not_allowed; present returns the declaration's member order. Do not sort by lexicographic ID. Validate summed selected capacity against integer party size; excess is 422 party_exceeds_capacity. Existing party_size exceptions and all time/grid errors remain unchanged.

Where multiple independent invalidities coexist, retain deterministic precedence: field conflict -> shape/member type/range -> duplicates -> excessive cardinality -> membership -> pair approval -> capacity -> existing time checks -> occupancy. Idempotency lookup remains earlier than all of these. Batch status/cutoff and non-occupancy precedence remain S1 input-order rules; do not globally prevalidate all move selections ahead of earlier bookings' cutoff checks.

Normalized selection equality compares ordered canonical IDs. A reversed declared pair input is the same selection; PATCH/move with unchanged time/party is a no-op and retains stored values. This is **different from receipt body identity**: array order is significant in parsed JSON, so the same key with reversed input array is 409 idempotency_key_reuse. table_id and singleton table_ids are also different request JSON bodies despite equivalent seating. Do not canonicalize request bodies using domain normalization before saving/comparing receipts.

## B. Availability, views and atomic state

S2 API/Concurrent bookings: build options by concatenating one singleton per fixture table, then one pair per declaration. Capacity is the table capacity or exact sum. At each S1 fitting local-time slot, filter options by party capacity and absence of any confirmed interval conflict on any member. Return `available_options` in that order, each `{table_ids,capacity}`. `available_table_ids` remains the ordered singleton subset only. Keep empty slots, closed-day behavior, first-fold/gap resolution and absolute durations unchanged. Sharing the same normalized option/overlap helpers prevents availability and write-validation drift.

New live reservation views always include copied `table_ids`; include table_id iff length is one, otherwise omit the property. Apply this to create, PATCH, list, lookup, cancel, batch responses and seeded bookings. Historical replay responses are an explicit exception: return their original JSON unchanged, even when it has no table_ids. Browser display adapts old receipts without modifying their stored JSON.

S2 reset accepts table_id or table_ids and honors status cancelled; absence defaults confirmed. Cancelled seeded records never occupy tables. Preserve all validation on invalid fixtures and replace only after complete construction. Cancellation changes one reservation status, so both members free at the same publication. PATCH builds the complete resulting record, checks occupancy excluding only its old identity and publishes once. Batch moves exclude old occupancy of every listed reservation, compare all resulting sets against each other and every unlisted confirmed record, then commit once. Unchanged listed bookings still occupy both members. Identity/owner/reference/created_at never change. Failed writes leave records, occupancy and receipt collection untouched. Retain the existing single-process synchronous `transact` boundary with no await inside; no additional lock service or database.

## C. Portable schema 2 and legacy receipt validation

S1 §10 and S2 Existing clients after an upgrade: exports retain `track:'tablekeeper', format_version:1`; state.schema_version becomes 2. Implement two clearly separated validation paths plus a detached migration:

1. Schema 1 input: validate using the **accepted Stage 1 semantics and historical response shape**, preserving credential F1 guards. Legacy request validation reads only Stage 1 recognized fields. A successful old request may contain an unknown `table_ids` field that Stage 1 ignored; do not reinterpret it as a conflicting Stage 2 field. Validate legacy receipts before migration without routing them through the new selector/view.
2. Clone the validated root. Set schema_version 2, add absent combinable arrays as empty, and mark each migrated receipt `response_schema_version:1` in internal metadata. Do not alter its body, canonical string or response. Existing users/hashes/scrypt parameters/sessions/bookings/reference/status/timestamps/start/end/rules remain identical. Internal singleton arrays already exist and need no reconstruction. Do not hash passwords or issue tokens again.
3. Schema 2 input: validate all live records with the new selection model. Each receipt carries response_schema_version 1 or 2. Validate version 1 receipts with the preserved legacy semantics, version 2 with Stage 2 semantics; do not compare a historical receipt to a current booking view. Only immutable identity/owner/creation properties must match the current booking; historical table/time/party may differ after later mutations. Schema 2 exports can legitimately contain both receipt versions.
4. Publish the entire validated/migrated state once; no partial account/session/booking replacement. Invalid state returns 422 without mutation. Reset erases all imported state. Repeat import restores the exact exported snapshot. Export returns a detached atomic snapshot. No source files, addresses, process secrets or shared volumes.

Stage 2 receipt validation must normalize pair sets before comparing proposed field semantics to a historical response. The current S1 batch checker uses direct value comparison for scalar fields; never extend it with array reference inequality, since distinct equal arrays would fail valid import. Compare normalized ID arrays structurally and preserve raw original body separately. A schema1 historical response must be rendered with the legacy singleton view, never the new table_ids view. A schema2 historical response uses the new view. Keep version markers out of API reservation bodies.

Old S1 receipts can contain unknown fields that later become meaningful; this makes versioning request **semantics** as important as versioning output shape. The response_schema_version marker denotes the operation's original contract, not the destination's version. All later imports must retain that distinction. No rewrite of accepted Stage 1 is needed.

A small application router with History API/popstate and four explicit routes suffices; preserve top-level session/booking state across route changes. React reducer/controller boundaries manage transitions; components render state rather than independently fetch overlapping data.

React documents stale response cleanup for Effect fetching; the stronger shared-generation contract below covers all related requests together ([React useEffect](https://react.dev/reference/react/useEffect)).

Keep server source/output separate from client: retain `src/` -> `dist/` for Node; use `web/` -> `public/` for Vite build (explicit absolute build output within stage root, no accidental cleaning of server dist). Add a browser tsconfig with DOM/JSX types; keep server tsconfig bounded to backend. `npm run build` typechecks both, compiles server and builds client. Runtime image copies server dist, production packages and public assets. Keep the accepted pinned base/USER node/PORT/0.0.0.0/no-network runtime contract. All fonts/scripts/styles/icons ship locally; system fonts are a compliant alternative. No service worker or background polling.

GET /, /signup, /login and /lookup return the same HTML entry with text/html; API paths keep application/json errors and never get an HTML fallback. Resolve static files from the dedicated build directory with path traversal protection, correct MIME types and a bounded route/file allowlist; missing /assets files are 404, not index.html. HTML uses no-cache; hashed assets can be cached. Required routes/assets are public. Do not put global bearer-auth handling ahead of HTML/static routing. Use root-relative same-origin API and asset URLs, never a build-time container host/port. Bundle all required screens eagerly so an already-loaded client need not fetch a deleted lazy chunk during an upgrade; never force a reload to recover a pending booking.

Proposed reusable modules: API transport/types; session provider; search controller/reducer; booking-attempt controller/reducer; lookup controller; application shell/router; authentication screens; search controls; availability option cells; booking form/feedback/confirmation; lookup detail. ## E. Session, search and request ownership

Session stores `{token,user_id,display_name}` in a top-level provider and optionally sessionStorage for same-tab direct route loads; choose sessionStorage in implementation. Catch unavailable storage and continue in memory. Signup/login replace this state only on confirmed success, and attach Authorization Bearer on protected calls. Public browsing works signed out. Render current-user on every signed-in route; logout removes local session and invalidates pending user-specific callbacks/forms. No server logout endpoint is required; other tokens remain valid. No cross-tab sync. An import is not a logout event; preserve the token/profile and pending form across it. A confirmed unauthenticated reply can request login; a network failure must not erase the session. Do not log tokens or put them in URLs.

Use an increasing `searchGeneration` and an immutable submitted query `{restaurant_id,date,party_size}`. On explicit new search: increment generation, invalidate old selectable results and old booking selection, capture the query, and start detail + availability requests concurrently. Publish **one complete bundle** only when both succeed and generation is still current. Grid, labels, dates/timezone, option identifiers and click handlers all read that bundle. Capture actual starts_at_local from the slot; never rebuild it from the browser timezone. Each catch/finally as well as success must check generation; a late failure cannot erase current results. Abort obsolete reads as an optimization, never as the correctness mechanism. A controls edit is draft state until search; show results' submitted query so draft changes cannot silently relabel old results.

When a new search replaces results, an old selected form cannot remain described as the new search. Clear its selection/feedback under a new form generation. If a booking request was already sent, stale callbacks cannot publish its result into the new form. No requirement to recover discarded attempts after deliberate new-search/navigation/reload; while the unchanged form remains, its retry identity must remain. An available cell signed out shows auth-error on the search screen (chosen option), with login/signup links; clicking unavailable does nothing. Returned list/detail errors have considered loading/empty/refused states for Designer; none may invent a slot or success.

## F. Booking-attempt state machine

Separate a selected form snapshot from refreshed grid state. Snapshot includes restaurant id/name/timezone, every selected table id/label, exact slot starts_at_local and party-size draft. An attempt includes unique attemptId, formRevision, owner user id, frozen request JSON, serialized body and random Idempotency-Key. Prefer legacy `table_id` for singleton submissions, `table_ids` in declared order for pairs; this lets an already-loaded Stage 2 client submit singles against Stage 1 during upgrade testing. Do not change singleton payload representation on retry.

| State/event | Required transition and visible contract |
|---|---|
| Selection or semantic field edit | Increment form revision; clear previous attempt/feedback/confirmation. Next submission captures a new body/key. A real edit invalidates the old attempt even if the user later changes back. |
| Submit with no attempt | Freeze current validated body/key before network I/O; state submitting. Keep form visible. Disable duplicate submits while this send is unresolved. |
| Retry/submit with unchanged attempt | Send the same body/key again, including after success. Do not satisfy repeat submit from a cached confirmation. |
| Valid 201 or replay 200 reservation JSON | State confirmed; remove booking-error and booking-uncertain; show server reference and details. Keep the selected form. Normalize legacy table_id to a display array only at the view boundary. |
| Confirmed HTTP rejection with structured error | State rejected; show booking-error, no confirmation for this attempt, no booking-uncertain. Preserve selected fields/body. Server failed keys remain reusable, so unchanged retry can reuse its key. |
| 409 table_unavailable | Above rejection plus one guarded availability refresh for the form's submitted query. Preserve form/inputs and error even if the selected option disappears. Never auto-select another seat or submit automatically. |
| Transport exception, timeout, truncated/non-JSON success | State uncertain; nonempty booking-uncertain, no booking-error or new confirmation. Preserve body/key/form. A client timeout cannot prove rollback. Retry remains available. |
| Any response for an obsolete attempt/form/user | Ignore it; never resurrect old success, error or uncertainty in a different form. |

Use a finite transport timeout with an explicit uncertain transition; 8 seconds is the chosen UI limit (server request limit remains 5 seconds). Search cancellation is safe; cancelling a booking fetch is merely an uncertain outcome. An already-successful attempt's next send should clear feedback/confirmation while pending so a subsequently lost replay response is presented consistently as uncertain, not a newly manufactured success. Store its identity so successful retry still retrieves the original reference.

A conflict refresh has a separate `refreshGeneration` plus captured searchGeneration/formRevision/attemptId. It updates only availability for the matching accepted bundle, not selection or booking feedback. If a new user search starts, or another refresh supersedes it, ignore old refresh success/error. Retain prior labels from the same restaurant; if refreshing detail too, publish its bundle atomically. This prevents a late refresh from restoring A after B. Do not make the form contingent on membership in the latest availability array.

Lookup has its own request generation; only the latest submitted reference owns detail/error. Fetch authenticated reservation, then corresponding public restaurant labels with the same lookup generation. Cancel only the current reference; on successful response show cancelled status and remove cancel button; on refusal show reservation-error without falsifying status. Encode opaque reference/restaurant path segments; render labels as text, not HTML. No browser PATCH/batch UI is required.
