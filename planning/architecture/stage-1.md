## Decision 1: one process, ephemeral state, atomic publication

**Chosen:** Node 24 LTS, TypeScript compiled during image build, Node HTTP server, `@js-temporal/polyfill` pinned to 0.5.1 with a committed package lock. The Node runtime supplies ICU timezone data. Start one process, one event loop; no worker or cluster owns application state. Later React/Vite assets can be compiled at build time and served by the same origin. React is a Stage 2 choice, not a Stage 1 dependency.

S1 §2 explicitly permits ephemeral state. Use one in-memory, JSON-compatible root state and synchronous copy-on-write transactions. `transact(fn)` clones the current root, runs all validation and mutations on the private candidate, constructs a detached response, then publishes the candidate with one root assignment only on success. Exceptions discard the candidate. There must be **no await, I/O, callback, yielding or asynchronous validation inside this transaction**. Reads capture one root and synchronously produce their response from it. No code outside the state module may mutate a committed root or returned response. Freeze roots in development and enforce the boundary in module APIs.

This gives a serial order at publication on Node's event loop, including overlapping writes, reads, batches, receipt claims and snapshot replacement. There is no interval where a read sees half a move. Make response JSON before allowing a later mutation; never retain a live mutable object in the HTTP response layer. A failed transaction cannot consume an ID counter, allocate an idempotency receipt or free occupancy. IDs may instead be cryptographically random and collision-checked inside the candidate.

Alternative: SQLite with explicit write transactions and an occupancy relation is valid, but is not chosen: it adds driver/locking/schema machinery without a restart-durability requirement. A mutable shared object plus asynchronous route handlers is rejected because a failed batch or an await between checks and writes can violate atomicity. This decision is conditional on modest fixture/state sizes: full-state copying is linear in retained state. No specified workload imposes unbounded data volume; measure actual 50-request HTTP tests before acceptance. Do not silently replace the state engine during implementation. A future measured bottleneck can justify structural sharing behind the same transaction API.

Authentication hashing is asynchronous **outside** transactions. Signup must recheck uniqueness against the current state inside its final transaction. Login must recheck that the same user and credential still exist before publishing its new token, so a reset/import during hashing cannot resurrect removed credentials. Reset builds a complete independent state, hashes fixture passwords outside a transaction, then publishes once; concurrent operations can serialize before its publication. Import validates/builds a detached replacement then publishes once. A monotonic in-process state generation can support these rechecks; it is not an exported business revision.

## Decision 2: internal model and exact external views

Keep JSON arrays for stable fixture order and exported collections; build derived Maps for lookups, never use untrusted IDs as prototype-bearing object keys. Export domain records, not runtime Map internals. Use stable generated IDs of at most 64 characters, collision-checked references of 6–12 uppercase letters/digits, and independent opaque random bearer tokens. References never change.

Internal state schema 1 contains:

- users: id, exact email, display name and a versioned scrypt credential; no plaintext password;
- sessions: exact opaque token and user id, supporting multiple non-expiring sessions;
- restaurants: original fixture values and ordered tables;
- reservations: stable id/reference/owner, restaurant, normalized `table_ids` array (one member in S1), party size, status, bare local start, resolved epoch start/end, created timestamp, and saved rule snapshot;
- receipts: user id, method, exact canonical route path, key, parsed original request JSON, canonical JSON identity and deep-copied original response JSON;
- internal state schema version and any counters actually used.

Save booking rule snapshots internally in S1 even though the S1 response must not expose S3 revision/terms fields. Save creation inputs/time for later history migration. Store scalar epoch milliseconds, not Date/Temporal instances or BigInts in portable JSON. Store output timestamps or deterministically render saved instants in the saved restaurant zone; preserve existing timestamps on import. A reservation's created_at is a UTC RFC 3339 timestamp with explicit offset. Seeded bookings preserve supplied identity/reference/owner; normalize their start/end once using fixture rules. They do not create completed-write receipts.

S1 views expose exactly the specified create-response fields, including table_id. Stage 2 adds table_ids and retains table_id only for a singleton. List includes confirmed and cancelled own bookings sorted by start instant descending; a stable id tiebreak is allowed. Public restaurant detail retains fixture shape. Never expose credentials, tokens, ownership internals or receipts on ordinary endpoints.

## Decision 3: time, grid, occupancy and cutoff

S1 §§4, 8–9: one `time.ts` adapter owns parsing, timezone resolution, formatting and date arithmetic. Validate exact regex shapes first (`YYYY-MM-DD`, `YYYY-MM-DDTHH:MM`, HH:MM), then use Temporal to reject impossible calendar values. Never use the server/browser timezone or `new Date(localString)` for local parsing.

Convert a valid PlainDateTime using `toZonedDateTime(zone, {disambiguation:'earlier'})`; roundtrip to PlainDateTime and compare with the input. Inequality means a nonexistent local time: 422 invalid_local_time. Equality chooses the earlier fold instant, which is required. Do not use disambiguation reject directly: it would incorrectly reject repeated times. Offset strings are produced without bracketed timezone annotations, with seconds and an explicit numeric offset. UTC may be formatted +00:00.

Build availability by iterating the **wall-clock grid** from the opening minute in slot_minutes steps, each local grid point once. Skip gap candidates. Resolve start and closing boundary to instants; add reservation duration in absolute minutes on the instant timeline and retain only candidates whose interval fits the opening window. Do not prefilter using wall-clock start plus duration, which is wrong at DST transitions. The slot grid is measured from local opening, independent of DST offsets. Closing/opening boundaries that exist use their first occurrence. For the unspecified case of a boundary in a DST gap, choose the first valid local minute at or after the boundary (a bounded search within that day); preserve the original wall-clock grid. Document this deterministic interpretation in RUN.md; required transition cases remain independently tested.

Occupancy uses half-open intervals: A overlaps B iff A.start < B.end AND B.start < A.end. A conflict requires an intersecting normalized table set and confirmed status. A booking at exactly another end is allowed. Availability includes every fitting slot even with no suitable tables; closed days return an empty slots array. Single tables retain fixture order. Capacity must satisfy integer party_size >= 1. Do not reject a create solely because its start is in the past.

Compute one `now` per write. A booking is editable only if now < currentStart - acceptedCutoffMinutes × 60000. Equality and later give cutoff_passed. Cancel an already-cancelled booking before cutoff checking and return its current view unchanged. PATCH of cancelled bookings is reservation_cancelled. PATCH uses the original current start for cutoff, then validates the full resulting selection/time/party values, excluding itself from occupancy. Publish release/reserve together. No-op PATCH still needs an editable confirmed booking; retain all values.

## Decision 4: request and validation ordering

Centralize an error constructor returning JSON `{error:{code,message}}`; set application/json; charset=utf-8 on JSON responses, including 4xx/5xx. Test controls return an empty 204. Route unknown resources with 404 not_found; catch unexpected exceptions at the HTTP boundary without leaking internals, but such exceptions remain test failures: a catch-all is not evidence that the no-5xx requirement is met.

Pipeline: route -> parse JSON object for body endpoints -> authenticate protected endpoint -> resolve required idempotency key -> endpoint-specific validation/resource checks -> transaction/response. Malformed JSON and non-object request bodies are 400 malformed_request. Required missing fields are 422; ordinary wrong body types are 400; correct type with bad format/range is 422. Exceptions: party_size is always 422 for non-integer, boolean or string; non-bare local timestamp **strings** are 422; local timestamp other wrong types follow 400. Batch moves has its own 422 shape rule for missing/non-array/out-of-range moves, non-object entries and non-string/duplicate references. Unknown body/query fields do not cause rejection, but remain significant in receipt JSON identity.

Missing or empty required Idempotency-Key is 400 missing_idempotency_key; over 255 characters is 422. Unauthenticated token is 401. A valid token belonging to a user without a reservation gets owner-private 404 for lookup/cancel/PATCH. No token on these S1 private paths gives 401. Unknown restaurant/table or wrong restaurant membership gives 404. Bad query party_size lexical forms such as 1e9, 4.0, +4 are 422; accept only plain decimal digits and validate the numeric range without overflow. Apply maximum ID length 64 wherever applicable, including fixtures. Do not add undocumented party-size maximums or future-only constraints.

For ordinary creates after replay resolution: validate required fields/types/formats, restaurant/table membership, party size and capacity, local instant validity, opening fit/grid, then occupancy. If a time is outside opening hours use outside_opening_hours; if inside but off-grid use not_on_slot_grid. A syntactically valid gap must yield invalid_local_time before grid/opening checks. The specification defines specific priorities for retries and batches, not every pair of independent errors; keep the remaining choice deterministic and test each required code in isolation.

Signup: local@domain form, password >=8, string display name, email duplicate 409 email_taken. Login missing/invalid schema uses shared validation; unknown account/wrong password yields 401 unauthenticated. Use exact email identity consistently; case normalization is not required by the spec. Public health, restaurant list/detail and availability do not require bearer auth. Reset/export/import are public test controls and remain enabled in the image.

## Decision 5: receipts and collective moves

S1 §7: receipt identity is the tuple (user_id, method, path, key), **not** merely (user,key). Same key on a different path is independent. Canonical JSON recursively sorts object keys but preserves array order, values and all unknown fields. Do not fingerprint only validated fields or raw bytes. Retain parsed request JSON as well as its canonical identity, allowing validation on import. JSON numeric spelling and whitespace/key ordering cannot distinguish receipts.

After parse/auth/header checks, consult the receipt inside the same state transaction before current resource or endpoint-field validation. A different JSON body gives 409 idempotency_key_reuse; identical body gives 200 with the deep-copied original response. A new successful write saves that response and mutation together, returning 201. No failure reserves a key. Retrying after resource cancellation, mutation or import must return the historical response, not a current serialization. Exactly one simultaneous identical request returns 201; others return 200. No response object may alias a mutable reservation.

S1 §11 moves: first validate 1..8 distinct string-reference item shapes. Process items in input order, resolving owner/private access and same restaurant, confirmed state and old cutoff **before** that item's proposed changes. Do all non-occupancy checks before any occupancy rejection, so a later item's invalid change beats an earlier item's overlap. Normalize each complete candidate without writing anything. For conflict checks, remove the old occupancy of **all listed reservations**, then check every resulting candidate against all other results and unlisted confirmed bookings. Unchanged listed items still occupy their original interval. This permits swaps while preventing conflicts with a listed no-op. Publish all records and the receipt once; return views in input order. On failure no old slot, timestamp, reference, receipt or counter changes.

## Decision 6: state portability and future migrations

S1 §10: envelope is `{track:'tablekeeper',format_version:1,state:{schema_version:1,...}}`. Envelope version stays 1 across stages; use internal schema_version 1..4 for team migrations. Export synchronously serializes one captured committed root, detaching the entire JSON snapshot. Export never changes state. Import accepts an unchanged team's export; validate the entire envelope, schema, record shapes, referential integrity, uniqueness, credential parameters, sessions, receipts and occupancy before one replacement publication. It must neither contact the source nor require shared disk, encryption keys or process addresses. Invalid JSON/type uses shared 400 rules; missing envelope fields, wrong track/version or invalid state is 422, leaving the old destination untouched. Valid import replaces every account/session/configuration/booking/receipt; repeated import returns precisely that snapshot. Reset removes even imported credentials and receipts.

Use Node crypto.scrypt asynchronously with N=16384, r=8, p=1, random >=16-byte salt, 32-byte result; store algorithm/parameters/salt/hash as strings and integers. Compare equal-length hashes using timingSafeEqual. All required credential verification material travels in the private export. Tokens are random opaque values stored in the state; no process-local signing secret exists to invalidate them on migration. Do not log exports/passwords/token values. Only synthetic fixtures may be retained as test artifacts.

Later migrations are pure functions over a detached imported state and cannot regenerate original receipt bodies, tokens, references, identities or timestamps. S2 introduces declared-pair selections and views; old singleton receipts remain byte-independent original JSON values without retroactive added fields. S3 materializes policy 0, accepted terms, revision 1 and created history from saved S1/S2 booking records. Earlier stages did not retain full amendment histories; migrate the observable imported record with a created baseline, without inventing unknown historical amendments. Preserve all prior receipts verbatim even if they lack newer fields. New writes/history use the new model. S3 needs policy selection by greatest effective_from <= local date, ties greatest publication version; real amendments use old cutoff then new-date terms, while no-ops preserve old terms. Store scheduled local dates separately from mutable starts for recurring occurrences. S4 adds stored closures/plans and deterministic solver results without changing the state engine.

Restaurant revision starts at reset 0 and tracks later specified operations; internal S1 counters may be maintained from the start to ease evolution, but are not exposed. S3/S4 transaction boundaries must increment each affected restaurant/series only once per compound action. Implementers must not derive revisions by counting receipts (replays and failed requests are different). Stage 4 planning may enumerate at most 10 seating options for 6 bookings, prune conflicts, and compare the exact lexicographic objective (moved count, unused seats, option rank vector). Preview state has plans only; applying checks stored restaurant revision and applied flag in the same commit that installs closure/assignments. This is an extension boundary, not authorization to implement Stage 4 now.

Stage 2 client seam: one monotonic search generation covers restaurant detail, results and selection; ignore any response from an older generation. Keep immutable submission body/key together across transport uncertainty and upgrades. A changed input creates a new attempt; unchanged retry reuses the exact original body/key. Distinguish unknown transport outcome from a confirmed HTTP rejection; never fabricate success. Designer must agree on selected form, loading/refused/uncertain states and their testids before frontend implementation. Same-origin bearer token state remains compatible through imports; do not clear it because the service version changes.

Use a Node 24 Debian slim build/runtime family with ICU; pin the resolved image version/digest during implementation and record it. Run unprivileged, bind 0.0.0.0, honor PORT/default8080, initialize empty usable state before /health returns 200. 3. Add create/own list/lookup/cancel/PATCH and receipt wrapper. Check ownership masking, inclusive cutoff boundary, no-op and rollback; 50 actual concurrent HTTP creates/identical retries, with one 201 and 49 original-body 200s for identical input.
4. Add batch prospective occupancy and deterministic non-occupancy precedence. Test swaps, unchanged blockers, mixed-owner/mixed-restaurant rejection and atomic failure including key reuse after rejection.
5. Add private-state export/import validation and migration hooks. Test independent process/port destination, existing tokens and hashed login, original receipts after later changes, replacing destination credentials, failed import leaves state intact, repeated import/reset.

Run the official isolated Stage 1 harness through the pinned interpreter as PM dispatches. Keep modules bounded: server/router, validation/errors, auth, time, store/serialization, domain reservations/availability, and tests.
