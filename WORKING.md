Every case below is **NOT_TESTED product behavior**, scheduled at the first clean, committed runnable Stage 1 candidate, before release acceptance. Run A (earliest HTTP): validation, occupancy, retries, moves, DST. Run B (same candidate, two independent service processes): export/import sequences. Preserve failures. Evidence names should carry case IDs; private snapshots/tokens stay ignored and never appear in room output.

Each run starts with its own synthetic reset fixture and logins. Default ordinary fixture: UTC, all weekdays 18:00–23:00, grid30, duration90, cutoff120, tables A/B/C capacity4 plus D capacity2 in that order, two users U/V, no bookings. Use future dates safely beyond cutoff for normal amendments and past dates deliberately for creation/cutoff tests. Fixtures with eight tables/bookings cover maximum batches. All rejection rows expect no change to records, occupancy or successful retry receipts; correct the failing body and reuse its key to prove failure did not consume it. Read-only calls expect no business-state changes. Successful write status and precise changed state are stated below.

Oracles use specification facts rather than service helpers: hand-enumerated grid lists; integer UTC-minute interval comparisons; literal numeric inequality/equality pairs sent as raw JSON; retained original response JSON for replay; before/after public records and availability for rollback. Snapshot internals may be read privately for structural/hash checks but are not the only behavioral oracle. Compare JSON objects without key-order sensitivity and keep booleans distinct from numbers. Equal-start list ordering is unspecified. Do not impose unrelated precedence where the source gives none.
