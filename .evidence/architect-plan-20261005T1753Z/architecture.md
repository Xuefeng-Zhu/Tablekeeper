## Decisions and boundaries

1. **Runtime:** Python 3.13 standard-library HTTP server, SQLite and zoneinfo. Bind 0.0.0.0:${PORT:-8080}. One process, threaded request handlers, one shared reentrant serialization lock and one SQLite connection. SQLite transactions atomically commit domain rows, journals, counters and receipts. Python avoids a native Node SQLite dependency and provides directly testable IANA handling. Keep React/Vite for the bundled Stage-2 UI; build its assets in a Node build stage and serve them from Python. Include timezone data in the runtime image explicitly, with a pinned tzdata package or copied system database. No runtime dependency installation, CDN, external font, authentication provider or hosted storage.
2. **Alternative:** Node/TypeScript API plus a timezone library and SQLite driver is compliant, but introduces two extra compatibility/build boundaries without a product need. A pure in-memory JSON aggregate is simpler but makes import validation and whole-state copy cost harder to bound. Neither alternative is needed unless independent implementation evidence disproves this runtime choice.
3. **Layers:** transport parses/routes/formats errors; validators implement explicit per-endpoint precedence; timezone adapter resolves local wall times; domain operations construct candidates; store owns transactions/serialization; response serializers are stage-specific; browser owns transient selection/retry identity only. No endpoint mutates another endpoint's response object. QA owns independent HTTP/browser oracles; Reviewer owns exact-candidate acceptance. Architect does not implement or accept its own product candidate.
4. **Container:** Stage 1 is a Python runtime image with all code and tzdata. Stage 2 adds compiled React assets; stages 3–4 inherit accepted prior files forward, then extend them. Every stage has independent Dockerfile/RUN.md/source; no shared parent-relative imports, volumes or hidden runtime assets. Health checks store readiness before returning the exact JSON. CPU/memory/startup/concurrency/request-timeout/no-egress compliance remains NOT_TESTED until isolated harness execution.

## Store and identity contract

Suggested private tables: metadata(schema_version), users(id,email,password_hash,display_name), sessions(token,user_id), restaurants(original_fixture,ordinal,revision), tables(restaurant_id,id,ordinal,label), reservations(id,reference,user_id,restaurant_id,table_ids,party_size,local_start,start_epoch,end_epoch,status,created_at,revision,accepted_terms), reservation_events(reference,seq,at,event,changes,resulting_revision,accepted_terms,plan_id), receipts(user_id,method,path,key,canonical_body,original_response), policies(restaurant_id,version,effective_from,complete_terms), series(id,user_id,revision,count,interval_weeks), occurrences(series_id,index,reference,scheduled_local_date,exception), plans(id,restaurant_id,base_revision,closure,assignments,applied), closures(restaurant_id,table_id,from_epoch,to_epoch,plan_id). Add only needed public functionality per stage.

IDs are opaque strings <=64 characters; use short random identifiers. References use secure random uppercase A-Z0-9 length 8–12, with a uniqueness constraint and bounded collision retries. Fixture ids/references/owners survive reset/import. Table order and combinable pair order are fixture metadata, never sorted alphabetically. Internal table selections are always canonical arrays: singleton or pair in declared pair order.

Store password hashes with hashlib.scrypt, random salt and encoded algorithm parameters; never store plaintext fixture passwords. Hash outside the serialization lock, then recheck unique email/commit inside it. Authentication token issuance commits before returning. Tokens are independent nonexpiring random values, and multiple sessions remain valid. Reset hash preparation is detached, then all tables including sessions/receipts/plans are replaced in one transaction. Do not log passwords, bearer tokens or real exports.

Begin an internal immutable journal in Stage 1 even though its history API is not exposed then: created record, actual changes, cancellation; store original values/timestamps and resulting counter. This small continuity record prevents migration from inventing earlier history. Store private policy-0 snapshots and private reservation/restaurant revisions from Stage 1; do not expose later-stage response fields prematurely. Preserve real no-op behavior. Seeded reservations begin at revision 1; restaurant revision after reset is 0, independent of fixture occupancy. Stage-1/2 amendments/cancels already maintain the hidden journal/counters needed for our own later migrations.

## Serialization, transactions and occupancy

All state-dependent operations, including auth reads, availability, health/store check, export, reset, import and write endpoints, enter one lock. Domain writes run one transaction under it; all validations/checks/allocations happen before commit. Reads observe either the complete before-state or complete after-state. A global lock is sufficient at 50 in-flight requests with bounded domain operations; do not introduce asynchronous check-then-write gaps. Expensive hash preparation and JSON syntax parsing may occur before lock acquisition; resource checks and replay resolution cannot.

Occupancy is always absolute UTC half-open intervals. Overlap iff a.start < b.end AND b.start < a.end. Compare every selected member of a singleton/pair. Cancelled rows never occupy. Closures use the same overlap primitive. Availability, create, amendment, batch, adoption, plan solver/application and series amend use this shared occupancy predicate, with separate independent QA expectations.

Batch operation: read originals; validate every item in specified input/index order without mutating originals; construct complete candidate rows; remove *all listed originals* from occupancy; check candidate-candidate and candidate-fixed conflicts; update all rows/journals/counters and receipt in one transaction. Keep unchanged listed reservations in the candidate occupancy check. Failure rolls back identities, rows, sequences, counters and retry claims. Generate ids only after validation or within a rollbackable transaction. Swaps must succeed when their resulting occupancy is conflict-free.

Restaurant revision increments once for new create, real individual amendment, first cancellation, policy publication, successful adoption, batch with any real change, plan application (even if zero moves), and series amend with any real change. It does not increment for fixture seeds, no-op patch/batch/series-amend, preview, failure or replay. Each affected series increments once per aggregate operation, never once per moved member.

## Request identity and errors

Parse strict JSON (reject NaN/Infinity); a required body must be an object. Keep the *entire* parsed body, including unknown fields, for replay identity, while ignoring unknown fields for domain validation. Missing versus explicit null is distinct. Object key ordering/whitespace is irrelevant; array ordering is meaningful. Booleans are distinct from numbers. Recommend exact-decimal numeric equality (1, 1.0 and 1e0 represent the same number), implemented with a typed recursive encoding and exact decimal coefficient/exponent normalization; no float rounding, truthiness equality or JSON.stringify shortcut. QA/Reviewer must independently challenge numeric lexical equivalence because the spec does not separately enumerate it.

Receipt unique scope is (user_id, METHOD, exact endpoint PATH, key). A key on another path is independent. Validate header existence/length after parse/auth and before replay resolution. Resolve an existing receipt before endpoint-specific fields, permissions and resource existence: identical canonical body => original JSON response with HTTP 200; changed body => 409 idempotency_key_reuse. Store only successful new operations, with HTTP 201; all 4xx leave key reusable. First success stores an immutable deep JSON value, not a reference to mutable domain rows. The same lock/transaction guarantees one 201 and the rest 200 for concurrent identical requests.

Generic precedence: syntax/object/type gate and caller authentication, then required key/range and replay gate, then endpoint-specific validation/checks in documented order. Distinguish 400 wrong JSON type from 422 correct type/invalid value. Endpoint exceptions override generic typing: invalid party_size of any type and bad local timestamp *strings* return validation_failed; wrong starts_at_local nonstring remains malformed_request. Query integers require plain ASCII decimal digits; no signs/exponents/decimal points. JSON integer-valued numbers must be positive/in-range and never booleans. Validate complete policies with their explicit blanket 422 rules. No user input produces an uncaught 5xx.

PATCH: owner/not-found gate; validate expected_revision as positive integer when present; stale check before cutoff/field validation; cancelled check and old accepted cutoff before resulting changes; no-op still requires editable confirmed state; then validate all resulting fields under the resulting date's policy. A repeated cancel returns current cancelled row before cutoff evaluation. Batch membership/shape/duplicate/same-restaurant checks precede per-item amendment gates; for each item in input order apply ordinary stale/cancelled/cutoff/field gates, then check occupancy only after all non-occupancy checks succeed. Do not let a first item's occupancy mask a later item's cutoff or format error.

Unauthenticated history, decision and GET series return 404 by their explicit exceptions. Other protected endpoints return 401; manager reads never grant another diner's private booking access. Resolve used receipts before current manager/owner/resource gates on idempotent endpoints once the caller is authenticated. For multiple simultaneous generic failures where the spec gives no relative order, choose a stable documented order; do not invent a new specific code.

## Time adapter

Strictly parse actual calendar dates YYYY-MM-DD and bare local YYYY-MM-DDTHH:MM; disallow offset/Z/seconds. For local input, produce both fold=0/1 candidates in the IANA zone, convert each to UTC and round-trip to local; discard candidates that do not reproduce the requested local minute. Zero => invalid_local_time; otherwise select the earliest UTC candidate. This handles skipped and repeated hours without hardcoding offsets. Deduplicate ordinary-time candidates.

Generate grid by local wall-clock minutes from opening, include each local minute only once, skip gaps. Resolve close independently. Add duration in UTC, then require the actual end instant <= closing instant. Serialize starts/ends by converting their UTC instants through the restaurant zone with explicit RFC3339 offsets; never add duration to a timezone-aware local datetime directly. Booking in the past is allowed. Cancellation/edit cutoff blocks at equality: now >= current_start - accepted_cutoff. Use a captured server UTC now per operation.

Policies select by booking's local start date, max(effective_from, policy_version) among eligible publications, else fixture version 0. Each reservation copies the full selected terms excluding effective_from and keeps its own end instant. Replans use each booking's terms, not latest restaurant capacities. Existing accepted terms never change on publication/cancel/reassignment/no-op.

Host probe evidence confirms Berlin/New York gaps, first folds and 90-real-minute ends. Must repeat timezone tests inside each runtime image; host Python/database success does not prove packaged tzdata.

## Snapshot and forward evolution

Export envelope stays track=tablekeeper, format_version=1, state={schema_version,...}. The internal schema discriminator is distinct from the mandated outer version. Export one fully materialized JSON snapshot under lock/transaction. Include hashes, salts/parameters, all sessions, original fixture order/config, immutable receipts (canonical full request bodies and exact original responses), rows, journal/terms/counters, and stage-supported policies/series/scheduled dates/exceptions/plans/closures. Do not embed process addresses, filesystem paths or database handles.

Import validates envelope and full private schema plus relationships in detached data before replacing live state. Reject wrong track/outer version, unrecognized/malformed schema, dangling relationships or broken invariants with 422 and retain the destination byte-for-byte semantically. Entire replace commits under the lock. Repeating import restores exported values without duplicate records. Invalid JSON/type rules remain as specified. Reset clears imported state and every receipt/session too. Exports containing credentials stay private, outside ordinary room output; synthetic snapshot validation is allowed.

Maintain explicit v1->v2->v3->v4 migration functions tested against actual prior-stage exported snapshots. v2 adds empty combinable when absent, canonical singleton selection and table_ids only to *current views*. v3 adds manager defaults/policy collection/series collection and exposes the already preserved private journal/revisions/terms. v4 adds empty plans/closures and exposes restaurant counters. Never regenerate IDs/references/tokens/timestamps; never transform stored original responses. Every later stage accepts all earlier schema versions from our own services. Migration has no dependence on old processes/ports/files. Imported original retry receipts can intentionally have earlier response shapes; current reads use the new serializer.

Upgrade acceptance exercises the same live browser/form/key across service import between requests, retained bearer token, lookup and committed-but-lost-response retry. A fresh fixture is not evidence of migration. Export followed by later source writes must not change the already materialized export.

## Browser contract (coordinate with Designer/Frontend)

Search state separates editable controls, request generation, and a committed result bundle {search parameters, restaurant detail/labels, availability}. Each search increments generation; accept all linked response results only if generation is current. Abort is optional optimization, never sole correctness. Grid cells, table labels and form selections derive from the committed same-generation bundle. A later A detail response cannot overwrite B labels. A new committed search closes or resets an old incompatible selection; late callbacks cannot restore it. Selection/form party size starts from searched parameters, not subsequently edited search controls.

Booking identity is a serialized full body plus generated key, scoped to current form fields. Unchanged submission—including after success, uncertain transport failure or service upgrade—reuses it. Changing a meaningful form field creates a new body/key and clears old feedback. On submission capture identity/generation; ignore stale response feedback after a newer form identity/search. Disable duplicate in-flight submit, retaining the form. Network error/lost response produces only nonempty booking-uncertain, no booking-error or manufactured confirmation. Confirmed API rejection produces booking-error. 409 table_unavailable refreshes current availability with the search race gate but preserves the selected form/inputs. Successful retry clears uncertainty/error and displays server original reference exactly. Never compute success from a locally cached row.

Represent idle/loading/selected/refused/uncertain/confirmed states explicitly, not several contradictory booleans. All required data-testid names are spec-owned; error/uncertain/confirmation nodes are conditionally present. Keep form on success. Table pair label comes from both human table labels in declared order; single cell IDs remain unchanged. Session token persistence may be localStorage; page-reload retry persistence/cross-tab sync is not required. Import does not reset browser state. API responses remain authoritative.

Designer owns warm visual hierarchy, 375px/desktop layouts, contrast/focus, consistent navigation and considered empty/loading/error states. Frontend must provide signup/login/current-user/logout and lookup/cancel, all required routes and testids, singles and declared pair options, without optional dashboards. No history/explanation/policy/plan/series screens are required. Stage 3 without explain omits explanation fields but retains inherited Stage-2 available_options; the contradictory shorthand “stage 1's shape” must not remove inherited combination behavior.

## Stage 3 immutable changes and agreements

History seq increments exactly once per real reservation mutation; event timestamps are UTC RFC3339 and nondecreasing (clamp to previous event time if host wall clock retreats). Created names table_id or table_ids, starts_at_local and party_size, in prescribed order, from null. A singleton->singleton change uses table_id; any changed seating involving a pair uses complete table_ids. Canonical reversed pair input alone is a no-op. Every entry copies resulting revision and terms; cancellation changes=[] and is terminal. Replays/no-ops/publications add no event. Decision/current views work after cancellation; owners only.

Adoption validates owner, anchor state, existing membership and old cutoff, then count/interval and each generated occurrence in index order (explicit overlapping-error order beyond stated rules must be challenged by QA). Anchor identity/revision/history/terms/created_at remain untouched; adding membership metadata is not a reservation change. Store scheduled_local_date for every occurrence independent of mutable current local start. Compute weekly dates with calendar arithmetic, never UTC + seven days. For adoption specifically, finish each generated occurrence's ordinary validation AND occupancy against fixed/previous generated candidates before examining the next occurrence: the first failing occurrence in index order controls the error. This differs from collective moves/series amendments, which give all non-occupancy checks precedence. Validate/commit adoption in one transaction; failure leaves no series/counters/refs/receipt. Commit one restaurant increment, series revision 1; distinct references. Individual real edits permanently set exception and increment series once; cancel increments series without setting exception; repeated/no-op/failure/replay does neither. Collective real diner moves set each affected occurrence exception and increment each series once.

## Stage 4 exact planner and application

Reject unsupported table/pair/considered-booking counts with planning_limit; considered set is all confirmed bookings overlapping proposed absolute half-open closure. Sort by ASCII reservation reference; fixed set includes confirmed rows outside considered. Candidate options enumerate singles in fixture order then pairs in declared order, with stable rank. Per booking filter by its accepted capacities, proposed/previous closures across full occupancy, and fixed bookings. Enumerate Cartesian assignments using depth-first search; prune candidate-candidate overlaps. Compare exact objective tuple (changed_count, total_unused_seats, rank_vector) and retain minimum. No greedy repair, random ordering or heuristic early winner. At most 10^6 unpruned complete leaves (10 options^6), with precomputed interval/option conflicts. Safe lower-bound pruning is optional; not required for initial correctness. Host enumeration 0.474 seconds only validates the basic bound, not the full isolated 5-second endpoint gate.

Canonical table-set equality determines changed flag. Preserve all considered rows even when unchanged. Persist preview plan containing base restaurant revision, normalized original closure, full assignment vector and result totals in a transaction that does not increment restaurant revision. No feasible plan stores nothing. Apply checks plan visibility/restaurant, already-applied status, then base revision freshness (replay has already been resolved). Same-key successful replay wins over these current checks. Commit closure and all assignments together; moved rows increment revision and append reassigned with table_ids, full before/after, plan_id and unchanged terms/times. Unmoved rows gain no history/revision. Increment restaurant exactly once; each affected series once; preserve scheduled dates and exception flags. Any restaurant mutation invalidates its older preview; other restaurants do not. Serial lock protects simultaneous apply/amend.

Series amend validates required expected revision/from_index/local_time, checks stale series revision before per-occurrence checks. Eligible indices >=from_index exclude cancelled and exception rows. Construct target local times on stored original scheduled dates and current table sets; no-op retains terms. Validate all non-occupancy errors in index order, then whole resulting occupancy against unchanged/fixed/closures. Commit changed rows/history once each, series/restaurant once total only if changed. Do not set exceptions. Empty/all-no-op succeeds with 201 and receipt without revisions. Imported series and operator-reassigned members use current tables plus preserved scheduled dates/flags.
